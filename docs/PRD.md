## 1. 문제 정의

### 1.1 근본 문제 — LLM은 세법을 지어낸다

세법 질의에서 LLM의 실패는 "모른다"가 아니라 **"그럴듯하게 틀린다"** 로 나타난다. 조문 번호, 해석례 문서번호, 심판례 청구번호는 형식이 규칙적이라 **환각하기 가장 쉬운 형태의 데이터**다. 그리고 이 분야에서 틀린 인용은 단순 오류가 아니라 **실무 산출물(경정청구서·의견서)에 실리는 허위 근거**가 된다.

### 1.2 파생 문제 3종 — 검색 도구만으로는 안 되는 이유

단순히 "NTS를 검색하는 도구"를 붙이면 해결되지 않는다. 실제로 결론을 뒤집었던 실패는 전부 **검색 이후 단계**에서 났다.

| # | 문제 | 실측 사고 |
|---|---|---|
| **P1** | **DB 수록범위 격차** — 법제처와 국세청은 서로 다른 것을 가지고 있다 | 부칙은 NTS에 **전용 컬렉션이 없다**. 해석례·기본통칙·집행기준은 법제처에 **없다**. 한쪽만 조회하면 반드시 누락된다 |
| **P2** | **시점(時點) 문제** — 조문은 시간의 함수다 | "지금 조문"과 "2023년 귀속 신고에 적용되는 조문"은 다르다. 게다가 **어느 시점본을 봤는가**와 **어느 과세연도에 적용되는가**는 또 별개다(후자는 부칙이 정한다) |
| **P3** | **규범 계층 미하강** — 조문에서 멈추면 답이 틀린다 | 조특법 §30 관련 **고시 §3②2호를 누락**해 결론이 반전됐다. 조문이 "고시로 정한다"고 하면 **답은 조문에 없다** |

### 1.3 추가 문제 — 도구 자체가 조용히 틀린다

- **계산식 증발** — korean-law `get_law_text`는 조문의 **계산식을 무언(無言) 누락**한다. 수식이 이미지(`flDownload.do`)라서다. 사용자는 누락된 줄 모른다.
- **오귀속의 데이터 승격** — 준용 대상을 잘못 귀속하면, 도구가 **경고 없이 틀린 조문의 부칙을 "준용 대상"으로 제시**한다. 침묵하는 것보다 나쁘다(능동적 오정보).

## 2. 사용자

**2계층 사용자 구조.** 이것이 이 제품의 설계를 좌우한다.

| 계층 | 정체 | 실제로 하는 일 |
|---|---|---|
| **직접 호출자** | LLM 에이전트 (Claude / Codex) | 도구를 호출하고, **도구가 반환한 ⚠ 지시를 따르거나 무시한다** |
| **최종 사용자** | 세무 실무자 (회계법인 등) | 답변을 실무 산출물(경정청구서·의견서·조서)에 옮긴다 |

> **설계 함의** 이 제품의 출력은 **사람이 읽을 답변이 아니라 LLM이 따를 지시**다. 그래서 도구 응답에 `⚠`·`── 후행 개정 확인 ──`·`nextActions` 같은 **행동 지시 블록**이 대량으로 들어간다. 순수 데이터 반환 API였다면 불필요했을 설계다.

## 3. 제품 경계 — korean-law-mcp와의 분담선

**이 분담선이 곧 제품 정의다.** 본 MCP는 법제처를 대체하지 않고 **보완**한다.

| 대상 | 1차 | 근거 |
|---|---|---|
| 현행 조문 본문 | **korean-law** | 법제처가 원본 |
| **계산식 든 조문** | **양쪽 필수 동반** | korean-law가 수식을 무언 누락 → 본 MCP `get_law_article(full=true)` |
| 법원 판례 전문 | **korean-law** | |
| 행정규칙 현행본 | **korean-law** | NTS 컬렉션 stale ⚠ |
| 세법해석례·질의회신 | **본 MCP** | 법제처에 없음 |
| 기본통칙 | **본 MCP** | 법제처에 없음 |
| 세법집행기준 | **본 MCP** | 법제처에 없음 |
| 시점본(year/efYd) | **본 MCP** | korean-law 연혁 회수가 사실상 고장(`get_historical_law` jo 추출 불능, efYd NOT_FOUND) |
| **부칙** | **본 MCP** | NTS에 없어 **법제처 DRF로 직접 조회** |
| 조문 diff | **본 MCP** | |
| 심판례 | **본 MCP** | |

> **비대칭 하나** 부칙은 법제처 데이터인데 본 MCP가 조회한다. NTS DB에 부칙 컬렉션이 없고, korean-law-mcp가 부칙 적용례를 조문 단위로 추적하지 못하기 때문이다. **DB 소유권이 아니라 기능 완결성으로 경계를 그었다.**

### FR-3 환각 방지 가드 (능동 경고)

**검색 결과에 자동 부착되는 행동 지시.** 사용자가 요청하지 않아도 붙는다.

| ID | 가드 | 함수 | 발동 조건 |
|---|---|---|---|
| FR-3.1 | 후행 개정 확인 | `buildLaterRevisionGuard` | 과거본 조회 시 현행본 자동 대조 → 변경/삭제/공포-미시행 |
| FR-3.2 | 하위 위임 감지 | `buildDelegationGuard` | 고시·시행규칙 위임 문언 (`대통령령`은 과발동 제외) |
| FR-3.3 | 준용 감지 | `extractJunyongTargets` | `준용` 앵커 + 「법령명」 **인접성 게이트** |
| FR-3.4 | 해석 분기 | `buildInterpretiveForkGuard` | 사후관리·추징형 4-AND 게이트 / 폐쇄 호구분형 |
| FR-3.5 | 행정규칙 stale | `ADMIN_RULE_STALE_NOTICE` | 훈령·예규·고시·지침 결과 포함 시 |
| FR-3.6 | 사문화 채점 | `assessDoctrineValidity` | 해석례의 현행법령 적용 가능성 8단계 |
| FR-3.7 | 구조개편 검출 | `detectPreRestructureCitations` | 옛 조번호 인용 → 현행 위치 매핑 + 자동 격상 |
| FR-3.8 | 적용시기 앵커 | `buildApplicationTimingGuard` | 과세연도개시기준·연중 시행일 ⚠ 강등 |
| FR-3.9 | 실패 가드 | `FAILURE_GUARD` / `notFoundResponse` | 예외 계열은 전문, NOT_FOUND는 전용 짧은 가드 — 둘 다 "추측·생성 금지" |

> **FR-3.4가 왜 필요했나 (실측 2026-06-14)** 조특법 §29의7② "청년 감소 → 제1항제1호 미적용"을 "제2호 = 원래 청년외 증가분만"으로 오독. **정답은 전체 증가인원 전부 제2호 단가**(기재부 조특제도과-215·서면-2023-법인-0978). 이 문언은 *공제 소멸*이 아니라 *단가 강등*을 뜻할 수 있다 — 문언만으로 산식을 단정하면 틀린다. 추징식(감소인원 × (상위호 − 하위호) = 프리미엄만 환수)과 forward 공제식의 정합성을 대조했으면 잡혔을 오류라, 이제 **능동 강제**한다.

### NFR-4 토큰 경제

이 제품에서 토큰은 1급 제약이다. 상한이 코드에 박혀 있다.

| 대상 | 기본 | full=true |
|---|---|---|
| 조문 본문 표시 | 6,000자 | 16,000자 |
| 준용 체인 블록 | 8,000자 | 24,000자 |
| INSTRUCTIONS | **2,000자 이하** | — |

- **상한 초과 시 cap을 올리지 않는다.** 대신 `── 생략 ──` 라벨 + **능동 재조회 안내**를 붙인다(v0.26.1 O2-2).
- INSTRUCTIONS 2,000자 제약의 이유: **호스트가 instructions를 ~2,000자 부근에서 절단하는 실측**. 그래서 치명도순 재배치 — 환각 방지 강제 절차가 앞, 응답 포맷이 뒤.

### NFR-5 보안

- **OC(법제처 API키) 마스킹** — `redactSecrets()` 전 출력 적용, 대소문자·URL인코딩(`%4F%43`) 변형 포함
- 표시용 URL은 `displayLawServiceUrl`로 **OC를 애초에 배제**, `redactSecrets`는 최후 방어선
- **ReDoS 차단** — `htmlToText`·`extractCdataText`를 선형 스캔으로 재작성. 실측 1M자 **68s → ms** (v0.26.0 SEC-4b)

### NFR-6 오류 처리

| 코드 | 의미 |
|---|---|
| `NOT_FOUND` | 검색 결과 없음 — **미존재 아님** |
| `INVALID_PARAMETER` | 파라미터 오류 (OC 미설정 포함) |
| `EXTERNAL_API_ERROR` | 상류 API 실패 |
| `PARSE_ERROR` | 응답 파싱 실패 |

실패 유형별 가드 2종(라이브 확인 2026-08-07):
- 예외 계열(`INVALID_PARAMETER`·`EXTERNAL_API_ERROR`·`PARSE_ERROR`) → `FAILURE_GUARD` 전문
- 검색 0건(`NOT_FOUND`) → `notFoundResponse` 전용 짧은 가드 **"⚠ 데이터 없음 — LLM은 결과 추측·생성 금지."** + `[RETRY_CANDIDATES]` L1→L2→L3

## 6. 설계 원칙

### 6.1 적용시기 해석 공리 6개

1. 신구 문구를 **나란히 대조** — 단일 시점본으로 단정 금지
2. 부칙 "개정규정" = **그 개정령이 실제 바꾼 문구 단위만**
3. 경과조치는 **자기 개정령만** 사정거리
4. **후행·특정 적용례 > 일반 경과조치**
5. **적극 문언 우선** — fallback 창작 금지
6. **서식·별지 < 부칙·법령 문언**

> **공리 적용의 한계** 적용례 anchor가 '최초공제연도'·'신고시점'형이면 **귀속연도만으로 판정 불가**하다. 차수(1차/추가공제)·신고시점을 사용자에게 되물어야 한다(조특법 §29의8 통합고용 등 다년 사이클).

### 6.2 데이터 정직성 원칙

| 원칙 | 실천 |
|---|---|
| **잘못된 매핑이 환각보다 위험** | `statute-restructures.json`에 **검증된 매핑만** 수록 |
| **미검증은 미검증이라 쓴다** | `credit-eligibility.json` `provisional: true` + note에 재검토 중 명시 |
| **오귀속 데이터를 무경고 승격하지 않는다** | EF-3 인접성 게이트 — 비인접이면 강등 + `lawHint` 라벨 |
| **해소 실패 시 창작하지 않는다** | `resolveCrossLawCtx` 5종 가드 — 정확 제명 일치만, 0건이면 안전 강등 |
| **검색 실패 ≠ 해석 부재** | 온포인트 해석이 없으면 hedge, literal로 메우지 않음 |

### 6.3 응답 5단 구조

① 결론(1~2문장) → ② 매트릭스(케이스별 결론+근거) → ③ 법령 래퍼(법률/시행령/기본통칙/해석례·심판례·판례, **출처별 분리 + NTS 원문 링크 필수**) → ④ AI 보충(⚠ 미검증, ①~③과 **섞기 금지**) → ⑤ "인용 본문 더 부착?" 1줄

빈 섹션도 헤더는 유지하고 "검색 결과 없음"으로 채운다(추측·생성 금지). 단답형은 생략 가능.

> **원문 링크 규칙** 검색행의 `원문:` URL을 **그대로** 쓴다. **임의 생성 금지.**

## 부록 — 릴리스 성격 분포

64개 릴리스 중 다수가 **"라이브 검증 후 정정"** 패턴이다. 이 제품은 스펙을 먼저 쓰고 구현한 것이 아니라, **상류 API의 실제 거동을 실측하며 가정을 계속 깨뜨려 온** 이력을 갖는다.

| 패턴 | 예 |
|---|---|
| schema 안내가 틀렸음을 라이브로 발견 → 정정 | v0.9.8 `taxLawCode` 305/306/307/313 재배치 |
| 배포 후 리뷰에서 P0 발견 → 즉시 픽스 | v0.26.0 EF-3 준용 오귀속 |
| 주석의 자기 기술이 사실과 달랐음을 정정 | v0.21.0 #G11 `redactSecrets` "장식 아님" |
| 실측 사고 → 능동 가드 신설 | v0.20.x 해석 분기 가드 |

**이 문서를 읽는 미래의 나/에이전트에게** — 코드 주석에 적힌 "확인됨"·"누출 경로 없음" 류의 단정은 **이미 한 번 틀린 적이 있다.** 결론에 쓰기 전 재확인할 것.
